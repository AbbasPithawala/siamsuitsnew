## Key architectural decisions

### Decision 1 — Quantity/per-unit modeling: no new schema (unchanged from the original pass)

`order_items` already has exactly the right shape: one row per super-product **instance** (`sequence` int, no `quantity` column — deliberately, per its own doc comment: *"e.g. 'Suit #1', 'Suit #2'"*). Phase 7's production ETL already proved this is correct by expanding every real legacy `{item_name, quantity: N}` into N independent `order_items` rows. **Nothing changes in `orders`/`order_items`/`order_item_components` for quantity itself.** `OrderBuilderPage.tsx` currently builds exactly one `CreateOrderItemInput` and never offers a quantity control — Phase 9's frontend work (Groups 5–7) materializes N independent `CreateOrderItemInput` entries client-side at submit time. This decision is unaffected by the measurement-sharing reversal below: units are still real, independent `order_items`/`order_item_components` rows for styling and manufacturing purposes — what changes is only *which draft state* (shared vs. per-unit) feeds each unit's component at submit time.

### Decision 2 — Fabric/Lining/Piping/Monogram: unchanged mechanism, Monogram Position's placement now goes through Decision 4's `render_slot`

`REWRITE_ARCHITECTURE.md` §2's unified `features`/`feature_products`/`styles`/`styleOptions` model already covers all four (`text` for fabric/lining code, `structured` for monogram, `choice` for piping), and Phase 7's ETL already backfilled real `fabric`/`monogram`/`"lining code"` (`text`/`structured`) feature data using this exact mechanism. Piping stays an ordinary `choice` feature rendered in the styling tab bar (this part is unchanged from the original pass — there was no placement objection to piping). **Monogram Position no longer gets its own ordinary tab** (the original pass's call) — see Decision 4; it's still modeled as its own real `choice` feature (own `featureId`, own `styleId` selection, own row in `order_item_component_features` — the *data* model is unchanged), only *where it renders* changes.

### Decision 3 — Measurements are shared per line item, not independent per unit (reversed from the original pass; real data-model consequence worked through below, not a text flip)

**Confirmed legacy behavior (unchanged finding from the original pass, now the adopted decision instead of the rejected alternative):** `Measurements.jsx` takes a `product_name` prop with no unit index; `Step4.jsx`'s `customerMeasurements[product_name]` is keyed only by product name, per component (a Suit's jacket and pant measurements are separate from each other, via `suitcustomerMeasurements`/`SuitMeasurements.jsx`, but each is still **one shared entry across all N physical units** of that line item's quantity — not per-unit). Only styling (`MissingFabric.jsx`'s `stylesArray[product.name + "_" + i]`, genuinely per-unit-indexed) varies per unit in legacy. **Decision: keep this exactly as legacy has it** — one measurement entry per (line item × component), shared across all N of that line item's units.

**The actual data-model consequence, worked through (not just "flip the decision text"):** `order_item_component_measurements` is keyed to `order_item_component_id`, which already is one-per-unit (each of the N sibling `order_items` gets its own real `order_item_components` row per super-product component). Sharing a measurement entry across N sibling units therefore needs *some* mechanism to get one shared value into N distinct component rows. Three options were weighed:

- **(Rejected) A new grouping table** (e.g. an explicit "cart line" id that N `order_items` rows reference, with measurements living at that level instead of on the component). This is the "true normalization" option — it would require inventing a persisted grouping concept that doesn't exist anywhere else in the schema today (currently nothing records "these N `order_items` rows were added together as one cart line"; that grouping only exists transiently in the frontend's cart-building UI). It also forces every downstream reader of measurements (manufacturing, QR/tag lookups, `assembleOrderDetail`, repeat-order cloning) to learn a second, higher-level place measurements can live, breaking the "everything about a physical piece hangs off its `order_item_component_id`" invariant the rest of the schema (and manufacturing_steps, QR tags, jobs) already depends on.
- **(Rejected) A nullable fallback column** on `order_item_components` pointing at a "source" component to inherit measurements from. Same grouping-concept problem as above, plus a real ambiguity a reader has to resolve at every access site (is this component's real measurement its own row, or do I have to chase a pointer first?).
- **(Adopted) Denormalize at write time**: no schema change to `order_item_component_measurements` at all. The *frontend* enters a measurement set once per (line item × component); at submit, the exact same values are copied into every one of that line item's N sibling units' matching `order_item_component_measurements` rows. Every unit ends up with a complete, independently-queryable, self-sufficient measurement set — identical to its siblings by construction, not by a live link. This is the same pattern Phase 7's ETL already used for historical data (*"a legacy order item... quantity: 3... all sharing the one styles[0] block... each unit now becomes its own `order_items` row"* — same "one shared source, N identical real copies" shape, just happening at order-creation time now instead of at ETL time). It keeps every existing reader (manufacturing, QR, repeat-order cloning, `assembleOrderDetail`) completely unaware anything changed — they already only ever read one component's own measurement rows. The real trade-off, stated plainly: editing one unit's measurements after the fact does not propagate to its siblings (there is no live link) — accepted, because that already matches how every other "snapshot at order time" field in this schema behaves (styles, fabric text, prices), and an order's recorded measurements shouldn't silently change out from under an already-placed order anyway.

**Consequence for Shoulder Type (Decision 4):** since Shoulder Type renders on the (now definitively single-entry-per-line-item) Measurements panel, its selection is *also* shared/denormalized across sibling units at submit time, using the exact same mechanism as the measurements it sits alongside — even though, as a `choice` feature, its value lives in `order_item_component_features` (the same table every other styling choice uses), not in the measurements table. Sharing granularity is a property of *which panel a field is entered in* (Measurements = shared; Styling = per-unit), not of which table stores it.

### Decision 4 — Shoulder Type / Monogram Position: a named "render slot," not an ordinary tab (reversed from the original pass)

The original pass modeled both as ordinary `choice` features rendered generically in the styling tab bar — fully generic, but a real, disclosed visual departure from legacy (which fixes Shoulder Type to the Measurements screen and nests Monogram Position inside the Monogram block, not as a tab). Rejected: keep legacy's real fixed placement.

**Mechanism: `features.render_slot`**, a nullable Postgres enum (`feature_render_slot`: `'shoulder_type' | 'monogram_position'`), default `null`. A hard enum, not a free-text/admin-extensible field, deliberately — this is a small, closed, system-defined set of "well-known roles" a feature can be assigned to, the same reasoning `orders.ts`'s own doc comment already gives for why `manufacturingStepStatusEnum` is a hard enum and `orders.status` isn't ("that set is fixed by the system, not by tenant configuration"). This is still fully catalog-driven and admin-configurable — an admin decides *which* feature (if any) plays each role, and on which products, via ordinary `feature_products` links, exactly as today — it just adds two named exceptions to the *default* rendering location, keyed by role, never by literal product or feature name in application code:

- **`render_slot = 'shoulder_type'`**: `<MeasurementForm>` (not `<FeatureSelector>`) looks up the product's features, finds the one (if any) with this slot, and renders it as a fixed image-radio section below the measurement grid (reusing legacy's `.fabric-types_NM`/`.fabricselection_Common_NM` classes) — not in the styling tab bar. Because Decision 3 makes the whole Measurements panel a once-per-line-item, shared-across-units affair, Shoulder Type's selection is naturally shared/denormalized the same way (see Decision 3's consequence note) — this is a side effect of *which panel it renders in*, not a second, separate sharing rule to remember.
- **`render_slot = 'monogram_position'`**: `<FeatureSelector>` finds the one feature (if any) with this slot, does **not** render it in the tab bar, and instead passes its real `styles` (e.g. "Left Side"/"Right Side") plus the current selection/`onSelect` callback down into `<MonogramFeatureField>`, which renders it as a small nested radio group inside its own layout — visually inside the Monogram block, exactly like legacy. This stays fully per-unit (Monogram, and everything nested in it, still lives in the per-unit Styling accordion — only its *tab-bar membership* changes, not its sharing granularity). The underlying data is unchanged from the original pass: still its own `featureId`/`styleId`, its own `order_item_component_features` row — `render_slot` only changes *where in the UI* it's composed, never how it's modeled or stored.
- **`<FeatureSelector>`'s generic rendering (both the inline text/structured zone and the choice-type tab bar) excludes any feature with a non-null `render_slot`, full stop** — it doesn't need slot-specific logic itself, just "skip anything with a role," so adding a third named slot later (if one is ever needed) doesn't require new branching inside `FeatureSelector`, only a new consumer that knows to look for it.
- Both seeded features get `is_required = false` explicitly (Group 0) — belt-and-suspenders alongside their exclusion from the generic tab-bar scan, so Group 8's validation-gate logic can't accidentally require them even if a future refactor ever scans "every choice feature with `is_required = true`" without first filtering by `render_slot`.

### Decision 5 — Two note fields, not one (reversed from the original pass; now falls out naturally from Decision 3)

The original pass consolidated legacy's two separate note fields (`Measurements.jsx`'s `customerMeasurements[product_name]["notes"]`, `MissingFabric.jsx`'s `stylesArray[...]["note"]`) into one `order_item_components.note` column. Rejected: keep both, as legacy has them. Given Decision 3, this now maps onto a real, meaningful distinction rather than an arbitrary duplicate: **`order_item_components.measurement_note`** (entered once per line item on the Measurements panel, shared/denormalized across sibling units exactly like the measurements it sits next to) and **`order_item_components.styling_note`** (entered per unit on the Styling accordion, independent per unit, exactly like every other styling field). The split isn't arbitrary preservation of legacy duplication — it's the same shared-vs-per-unit distinction Decision 3 already introduces, just applied to a text field instead of numeric measurement values.

### Decision 6 — File storage service (unchanged from the original pass)

Confirmed: **zero** storage/upload code exists anywhere in `server/src` today (`env.ts` has the `AWS_*` vars plumbed as `optional()` placeholders since Phase 1/2, never consumed). `StyleOptionButton.tsx`'s own doc comment already flags this as a known gap. Legacy uses Cloudinary (`REWRITE_ARCHITECTURE.md` §4 already calls this out as a secrets problem to fix); the target architecture already locked "storage service abstraction for S3" as the replacement. Phase 9 needs real reference-image upload (per-unit, two-step: local preview then a separate "Upload" call) and therefore has to build this now — **built as a generic, order-agnostic service** (Group 1) so Phase 8 Group 4's still-open feature/style-image-upload gap can consume the same thing later instead of a second implementation appearing. Local-disk backend by default (dev/test/CI, no real AWS dependency); S3 backend behind the same interface, gated by the already-present optional `AWS_*` env vars.

```ts
        ...(unitComponentDraft.referenceImage ? { referenceImage: unitComponentDraft.referenceImage } : {}),
      };
    });
    items.push({ superProductId: lineItem.superProductId, components });
  }
}
```

One `CreateOrderItemInput` is pushed per unit (the inner `for (const unitStylingDraft of lineItem.stylingDrafts)` loop) — `stylingDrafts.length` units produce `stylingDrafts.length` items, with no `quantity` field ever sent. `measurements`/`measurementNote` come only from `lineItem.measurementsDraft` (the one shared draft, read fresh inside the unit loop but never varying by unit — this is what makes every sibling unit's copy byte-identical by construction, not by a live link). `features` concatenates the unit's own styling `FeatureValue[]` with the shared draft's `features` (which in practice only ever holds the Shoulder Type entry, per `LineItemMeasurementsPanel`'s own doc comment) before `sanitizeFeatures` — this is the literal implementation of "Shoulder Type travels with the shared measurement data, even though it ends up in the same `features[]` array as per-unit styling choices."

**Repeat-order prefill re-hosted for the cart shape:** groups `repeatSource.items` by `superProductId` (a repeat source can have several sibling `order_items` from the original order's quantity — each group becomes one `LineItemDraft`, `stylingDrafts.length` matching the group's real size). The shared measurement draft is seeded from the group's first item's components (every sibling is byte-identical by construction, so any one is representative); each unit's styling draft is seeded from its own source item's components. One disclosed, narrow simplification: the Shoulder Type `FeatureValue` is **not** split back out of a repeat source's flat `features[]` into the shared draft (that would need a feature-catalog `renderSlot` lookup this synchronous, render-time prefill doesn't have convenient access to) — it round-trips forward unchanged as part of each unit's own per-unit styling draft instead, which is exactly what the pre-Group-7 code already did (it never split shared-vs-per-unit data at all). No data is lost, only its shared/per-unit *classification* during a follow-up repeat-and-edit session — a cosmetic/organizational nuance, not a functional regression, and out of this group's stated acceptance criteria (which is about fresh cart-based order creation, not repeat-prefill precision).

**Orders mapping — the judgment calls, since this was flagged as the highest-risk part:**
- **Super products didn't exist to migrate into.** Legacy has no `SuperProduct`/bundle concept at all (`"Suit"`/`"Tuxedo"` were hardcoded `if/else` branches in the old order code) and Phase 2's catalog ETL correspondingly never created any `super_products` rows. Every legacy `order_items[].item_name` — bundled (`suit`, `tuxedo`) or standalone (`jacket`, `pant`, `shirt`, `vest`, `overcoat`, `tuxedojacket`) — is required by `orders.service.ts` to resolve to a real super product before an order can exist at all, so `catalog.ts#ensureSuperProducts` creates the 8 real ones deterministically (idempotent, matched by name) from how those 8 item names are actually used across all 221 production orders. This is populating catalog data through the exact mechanism `REWRITE_ARCHITECTURE.md` §2 already specifies for this ("an admin names a super product and attaches 1 to 3 products to it") — not a new table/column.
- **`quantity` > 1 on a legacy order item is N identical physical units, not N array entries.** Discovered by chasing a real resolution failure: a legacy order with one `order_items` entry `{item_name: "shirt", quantity: 3}` has manufacturing/style keys `shirt_0`/`shirt_1`/`shirt_2`, all sharing the one `styles[0]` block (legacy never varies styling per unit). Each unit now becomes its own `order_items` row (matching the schema's own "one row per super-product instance — Suit #1, Suit #2" comment), all identically styled. Verified live: `EDW-N-00012` (2 suits + 2 shirts) now has exactly 4 real `order_items`, not 2.
- **Fabric and monogram had no catalog feature at all to migrate into — not a schema gap, a Phase 2 data gap.** `REWRITE_ARCHITECTURE.md` §2 specifies fabric as `type: text` and monogram as `type: structured`, but Phase 2's catalog ETL never actually created either feature for any product (confirmed directly against Postgres — zero `fabric`/`monogram` features anywhere in the real catalog). Since `fabric_code` and `monogram` are present on the large majority of real order items (547 and 491 of 551 item-instances respectively) and the schema's unified feature model already fully supports `text`/`structured` types for exactly this purpose, this ETL backfills the missing `fabric` and `monogram` features per product (idempotent, no styles/pricing involved) rather than silently dropping that data. **Flagging this explicitly per the boundary rule**, even though it's implemented: this is new *data* in an existing table using an already-designed mechanism, not a new table/column — if the architect wants it done differently, it's an easy follow-up to redo.
- **`lining_code` is a free-text fabric/lining code in real data, not a match against the pre-existing "lining" choice feature.** Phase 2 created a `type: choice` "lining" feature (3 styles: "no lining"/"regular lining"/"half back lining" — a construction-style choice with real `workerPrice`s). Real order data's `lining_code` values are overwhelmingly free-text supplier codes ("sss-pht-htciv-50", "pvl #31" — checked across all 370 real occurrences), not those 3 choices. Rather than risk misattributing real pricing-bearing style rows, this ETL stores `lining_code` as a new `type: text` **"lining code"** feature (distinct name from the existing "lining" choice feature, so both coexist without collision) — flagged the same way as fabric/monogram above.
- **Piping and style/groupStyle choices needed fuzzy matching, not exact-string matching, to avoid a huge false-skip rate.** First full run: 84 orders skipped entirely, almost all on "jacket lapel"/"collar"/"shirt cuffs" — not a data gap, a real bug-shaped mismatch: the catalog's styles are base names ("notch lapel") while real orders qualify them with detail the catalog doesn't carry ("notch lapel 4.25 inches"). Fixed with word-set-overlap matching (`catalog.ts#findStyleForFeature`, after stripping numbers/units) that prefers the most specific candidate; a fuzzy (non-exact) match keeps the full original text in `textValue` alongside the matched `styleId` so no detail is lost. This dropped whole-order skips from 84 to 2 (both the orphaned-retailer case, unrelated). Piping uses its own prefix match (catalog style names are `"<code> (<supplier>)"`, legacy stores the bare code).
- **`manufacturing_steps` status/tailor/timestamps are driven entirely by the legacy `jobs` collection, not the `orders.manufacturing` blob.** The blob is a denormalized cache with at least one confirmed corruption in production data (a `"[object Object]"` process key from a real historical bug) and an unreliable middle-segment naming scheme for bundled items (a tuxedo's jacket-slot key is `tuxedo_jacket_0` in some orders, `tuxedo_tuxedojacket_0` in others). `jobs` has a clean `process` ObjectId reference and is the actual source `assignNextStep`/job-cost data came from historically, so `manufacturing.ts` resolves state from there — a step with no matching job simply stays `"pending"` (correct: a step never assigned never got a legacy Job document either).
- **Settlements/extra payments preserve legacy's historical dollar amounts exactly, never recomputed.** `createSettlement`'s live formula recomputes `subTotal`/`totalPay` from today's `jobs`/`extraPayments` rows — reusing it for historical migration would silently rewrite history if a category's cost or a style's `workerPrice` has changed since. This ETL inserts the legacy `subTotal`/`deductedAdvance`/`rent`/`manualBill`/`totalPay` values as-recorded.
- **No persistent legacy-id mapping file needed except for `customers`.** Retailers/tailors/orders/order_groups/extra_payment_categories/extra_payments/settlements/jobs all resolve via a real natural key already in the new schema (`code`, `username`, `order_number`, or a composite tuple) or are fully re-derivable at read time by replaying the same resolution logic (`legacy-item-resolution.ts`) — consistent with the correction that a `legacy_mongo_id` schema column is off the table. `customers` genuinely has no natural key on either side, so it's the one domain tracked in a small untracked JSON file (`server/src/db/etl/.state/`, gitignored) scoped entirely to this script, per the persona's stated fallback option. It's self-healing: if the file ever points at a row that no longer exists (e.g. after a manual truncate-and-rerun during testing), the affected customer is simply re-migrated rather than the run failing.

**`customFittings`/`style_options.thai_name` gap investigation — no change to Phase 2's deferral, but two *new*, smaller gaps found and flagged instead:**
- `customFittings` (18 legacy docs): confirmed no real order anywhere references a custom-fitting id — it's a standalone admin-defined fitting-preset catalog (e.g. "slim" = named measurement offsets), never actually applied to an order in production data. Half its `product_id` references are already orphaned (product deleted from legacy since). Safe to continue leaving deferred — nothing customer-facing depends on it.
- `style_options.thai_name`: not referenced anywhere in real order data either (legacy orders record chosen `styles` directly, never a sub-`style_option`). Confirms Phase 2's original deferral is still fine.
- **New gap found while investigating (not previously flagged): customer-level saved measurement profiles.** 149/624 customers have a populated `measurementsObject` (and 116/73 a `suit`/`tuxedo` shortcut) — a "remember this customer's measurements for next time" convenience, separate from any actual order's own measurements. The new `customers` table has no measurement fields at all; every *order's* real measurements are still fully captured (migrated into `order_item_component_measurements`), so no order/manufacturing/payroll data is at risk — only this pre-fill convenience is not carried forward. Flagging per the same standard as `customFittings`, not silently dropping it, and not inventing a table for it without confirming that's wanted.
- **New gap found: per-order free-text tailoring notes.** 353 of 551 real order-item instances carry a `note` field (e.g. cutting/lapel/pocket instructions). `order_item_components` has no free-text notes column in the new schema. Not fabricated into an existing JSON field (e.g. stuffed into the monogram payload) since that would conflate two unrelated concepts and only covers components that also happen to get a monogram feature. Flagged for an explicit decision rather than worked around.

**Follow-ups flagged, not actioned (all non-blocking):**
- Fabric/monogram/lining-code feature backfill and the piping fuzzy-match: reasonable, low-risk calls, but genuinely new judgment this phase made rather than something Phase 2 or the architecture doc explicitly specified — worth a quick architect glance.
- Customer-level saved measurement profiles and per-order free-text notes (above): real data, no schema destination, deliberately not invented here.
- Retailer *login* accounts were not created — this ETL only migrates the `retailers` business-entity rows (per the architecture's deliberate retailer/user split), not `users` rows for retailer staff to log in with. Whether/how existing retailers get real logins on the new system is a separate rollout decision, not a data-migration one.
- 84 individual feature/measurement values (listed above) still don't resolve to any catalog equivalent after fuzzy matching — genuinely absent catalog options (e.g. "interchange cuff"), not a matching bug. Would need either catalog additions or accepting the gap.

**Findings that are not gaps, documented rather than papered over with a misleading test:**
- **Order creation has no money field at all** — `orders`/`order_items`/`order_item_components` carry no price/total column (confirmed against `server/src/db/schema/orders.ts` and `orders.routes.ts`'s `createOrderSchema`). - **Invoicing is not data-linked to orders/jobs** — confirmed against `server/src/db/schema/invoicing.ts`'s own comment ("ported relationally with no behavior change from the legacy Mongo shape") and `invoices.service.ts`: `retailer_invoices.lineItems` are freeform `{description, quantity, unitPrice}` entered directly by a retailer-billing admin, not derived from any specific order/job. So there is no "job cost flows into an invoice" transition in this codebase to test — invoicing is a separate, freestanding retailer-billing feature, same as legacy. Not a gap; a data-model fact worth recording so a future reader doesn't go looking for a link that was never built.
- ~~**Flagged, not fixed (outside this group's scope — a business-rule decision, not a test-coverage gap):** `createSettlement` itself does not check that a job's underlying `manufacturing_steps` row is `complete` before allowing it into a settlement~~ — **fixed directly, 2026-08-11**, immediately after this audit, since paying for unfinished work is a real money-safety gap, not an ambiguous business-rule call (there's no legitimate scenario where settling an in-progress job is correct — the legacy system's whole "half-enforced" job-completion problem, per `FUNCTIONALITY_OVERVIEW.md`, is exactly the kind of gap this rewrite exists to close). `createSettlement` (`payroll.service.ts`) now checks `requireOwnedJob`'s returned `step.status === "complete"` and rejects with `409 JOB_NOT_COMPLETE` otherwise, at zero extra query cost (the step was already being fetched for ownership). This broke 6 existing test call sites that settled a merely-`assigned` job (via a shared `createSettleableJob` test helper whose own docstring already incorrectly claimed it completed the job) — fixed the helper to actually call `completeStep` by default (with an opt-out for the one test that deliberately needs a still-assigned job), added `factory.jobs.complete` to the route-test fixture's permission set, and added a new dedicated test (`payroll.service.test.ts` → "rejects settling a job whose manufacturing step is only assigned, not complete") plus verified the full server suite: 208/208 passing.

**Verification:** `npx tsc -b` — zero errors. `npm test` (fresh `npm install` run first, no lockfile conflicts with the concurrent Group 0 ETL work) — 207/207 passing across 31 files (up from the pre-existing 205; the 2 new tests above account for the difference).

## Group 2 — Deploy pipeline for the new stack

Depends on: nothing functionally, but do after Group 0 has real row-count numbers to reference in verification docs. Parallel-safe with Group 1.

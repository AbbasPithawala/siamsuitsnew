# Workstream B — Legacy PDF fidelity audit

## Audit method

Read `siamServer/retailer/routes/routes.order.js` lines 1739–2900 (`POST /createPdf`) in full, and `server/src/services/orderPdf.service.ts` (312 lines) in full. Findings below are from direct comparison, not inference from either file's comments.

## Confirmed covered (present and functionally correct in `orderPdf.service.ts`)

- **QR codes per component** — present, and structurally *improved* over legacy: encodes the real `order_item_components.id` UUID directly (`QRCode.toDataURL(component.id, ...)`) instead of legacy's `orderId + "/" + itemKey` string built by splitting `item_code` on spaces and subtracting 1 — this is `REWRITE_ARCHITECTURE.md` §2's own "QR/tag redesign" decision, already implemented.
- **Generic per-component walking** — `renderItemSection`/`renderComponentSection` iterate however many real components a super product has (1–3), with zero product-name branching — matches `REWRITE_ARCHITECTURE.md` §5 Phase 6's stated goal ("PDF generation rewritten to walk components generically instead of suit/tuxedo special-casing"), which legacy's own `item_name == 'suit' ? ... : item_name == 'tuxedo' ? ... : ...` branching (repeated 10+ times across the file) never did.
- **Measurement table** (name/value/adjustment/total) per component.
- **Feature/styling data present in some form** for every feature type (choice/text/structured), via one generic table — see "Missing" below for the real fidelity gap in *how* this is presented for two of the three types.
- **Basic order metadata**: order number, retailer name, customer name, status, type, rush flag, repeat flag, order date.
- **Manufacturing step status per component** — not in legacy's PDF at all; a disclosed enhancement, not a gap.

# Workstream C — Shared pagination

## Key architectural decision — page-based, not cursor-based; two distinct rollout modes

**Page/pageSize query params** (1-indexed `page`, `pageSize` capped at 100, both `z.coerce.number()`), not cursor-based. Justification: every existing `listX` service function already has a deterministic `ORDER BY` (per-entity, e.g. `desc(orderDate)`, `asc(name)`) that page/offset composes with directly; this is an internal admin tool at per-tenant scale, not a high-concurrency public feed, so cursor pagination's real advantage (stable pages under concurrent inserts) isn't worth the complexity of inventing an opaque-cursor encoding this codebase has no other precedent for; and MUI v5's own `TablePagination` (already the UI kit in use) is a `page`/`rowsPerPage` component, so the frontend side maps almost 1:1 with no adapter layer needed.

**Response envelope**: extends (doesn't replace) the existing `{ data: [...] }` convention — becomes `{ data: T[], pagination: { page, pageSize, total, totalPages } }` on endpoints that opt into paginated mode.

**Real design tension, worked through, not glossed over**: several endpoints (`GET /products`, `GET /super-products`, `GET /features` with no `productId`, `GET /measurement-definitions`, `GET /processes`) are called by **two different real consumers today** — the admin table page (which should be paginated) *and* the order-builder's own pickers/dropdowns (`ProductsPage.tsx`'s `useListProductsQuery()` and the order-builder's own identical call are the literal same RTK Query hook, same endpoint, no `productId`/filter distinguishing them). If pagination defaulted to "page 1, pageSize 25 when params are omitted," every unfiltered picker in the order-builder would silently start receiving only 25 rows the moment this ships — a severe, easy-to-miss regression. **Decision, split by endpoint category:**
- **Dual-purpose catalog endpoints** (Products, Super Products, Features with no `productId`, Measurement Definitions, Processes): pagination is **opt-in** — omitting `page`/`pageSize` returns the full unpaginated list exactly as today (preserves every non-admin-table caller); the admin table pages are updated to always pass explicit params.
- **Single-purpose endpoints** (Customers, Retailers, Orders, Invoices, Shipping Boxes, Tailors, Users, Roles, Extra Payment Categories, Order Groups) — nothing else in the app fetches these unfiltered for a picker — pagination is **mandatory**: `page=1&pageSize=25` applied even when the params are omitted, which is what actually fixes the unbounded-growth problem on these.
- **Explicitly out of scope, either mode**: nested/bounded sub-resource lookups scoped by a parent id — `GET /features?productId=`, `GET /products/:id/measurements`, super-product components, styles-by-feature, style-options-by-style, fitting-values-by-fitting. These are option-lists a picker consumes as one full in-memory set, bounded by catalog size (tens of rows), not tenant order volume — paginating them breaks every dropdown consumer for no real benefit.
- **Job Assignment / Payroll Settlement pages**: their exact underlying query wasn't pinned down precisely in this research pass (no `listX`-named export was found backing them the way every other page has) — flagged for whoever picks up Group 3/5 to confirm whether they're genuinely unbounded tenant-wide lists (in scope) or already-bounded per-tailor/per-queue views (out of scope), rather than guessing here.

# Workstream D — Customer measurement profile

## Key architectural decisions

**1. Schema shape** — `customer_measurement_profiles` (id, tenant_id, customer_id → `customers.id`, product_id → `products.id`, timestamps, soft-delete — matching every other top-level tenant table's convention; unique on `(tenant_id, customer_id, product_id)`) + a child `customer_measurement_profile_values` (id, profile_id, measurement_definition_id, value, adjustment_value, total_value — the identical numeric-column shape `order_item_component_measurements` already uses, per the user's own instruction to mirror it; unique on `(profile_id, measurement_definition_id)`). One row per measurement definition (not a JSON blob), matching this schema's existing convention for exactly this kind of per-measurement-definition data.

**Decided (2026-08-16), not open**: Shoulder Type (or any other `render_slot` feature) is entered on the same Measurements panel and shares Decision 3's "shared per line item" sharing granularity, but this profile stays scoped to plain measurements only, permanently — `customer_measurement_profile_values` mirrors `order_item_component_measurements`'s shape exactly and nothing else. Folding in `order_item_component_features` would be a second, separate shape decision the user has explicitly declined to make in this phase. Not a deferred/open item — do not build a Shoulder Type carry-forward under this table.

**2. Write path** — hooks into `buildOrder`'s existing per-component insert loop in `orders.service.ts` (`server/src/services/orders.service.ts`, the loop that already inserts each component's `order_item_component_measurements` rows), in the **same transaction**, not a separate post-commit step or a second `withTenant` call (Phase 8 Group 1 already found and fixed a real bug from exactly that mistake — a nested transaction reading stale pre-write data — so this must reuse the caller's own `tx`). Concretely: for each component, upsert the `(tenantId, order.customerId, component.productId)` profile row (insert if absent), then **per-row upsert** (`INSERT ... ON CONFLICT (profile_id, measurement_definition_id) DO UPDATE`) each submitted measurement into `customer_measurement_profile_values` — **not** a full-replace-delete-then-insert the way `setProductMeasurements`/`setFeatureProducts` work elsewhere in this codebase. This is a deliberate difference, called out explicitly so a future reader doesn't "fix" it to match those: `product_measurements`/`feature_products` are admin-defined *link sets*, where "not in the new list" unambiguously means "remove this link." A customer's measurement profile is being incrementally refined order-by-order — a given order's submission omitting a measurement (e.g. the tailor didn't re-measure something unchanged) must not be read as "delete this from the customer's known profile." Per-row upsert-only-what's-provided preserves everything else.
   - Applies uniformly regardless of whether `resolvedItems` came from `resolveItemsFromInput` (fresh entry) or `cloneItemsFromOrder` (repeat order) — both funnel through the same single insert loop, so a repeat order also refreshes the profile (a no-op in the common case where the values already match; a real re-sync if the profile was hand-edited or predates this phase out of band). This is a natural consequence of hooking at the one shared insert point, not a policy needing separate justification.
   - Atomic with order creation by construction (same `tx`) — no new failure mode; a rolled-back order creation rolls back the profile write with it.

**3. Read path** — pre-fill triggers at the point `LineItemMeasurementsPanel`/`MeasurementForm` (Phase 9 Groups 3/6) already fetch `useProductMeasurementsQuery(productId)` per component: add a sibling `useGetCustomerMeasurementProfileQuery({ customerId, productId })` call at the exact same spot, and when it resolves with a real profile, seed the draft's initial `value`/`adjustmentValue` from it — same UX shape as Phase 8 Group 6.4/Phase 9 Group 3's Manual Fit pre-fill (a real, editable value populates the form; the tailor can freely overwrite it, it is never read-only). **Not** triggered at customer-selection (Step 2) alone — no `productId` is known yet at that point, so there's nothing to look up. In this wizard's actual structure, "on selecting the product" and "when the Measurements panel mounts" are the same real moment (a super product's components, and therefore their `productId`s, are only known once a line item exists in the cart, and the Measurements panel only mounts once that line item is focused) — so there is exactly one real trigger point, not two competing ones.
   - **Precedence with Manual Fit, worked through**: no real conflict exists once the two are examined — a profile pre-fills `value` (the customer's actual body measurement), while a Fitting (Manual Fit) only ever writes `adjustmentValue` (a garment-level preset delta, per its existing Phase 9 contract) and is applied afterward as an explicit, tailor-triggered opt-in. Different columns, different axes — the profile does not get silently clobbered by a subsequent Manual Fit selection, and no ordering/precedence rule needs to be coded, only understood.

# Workstream E — Retailer RBAC redesign

## Current-state findings (verified directly, not assumed)

- **`retailer_users` (the M:N user↔retailer join table, present since Phase 1) is completely unused** — zero services, routes, or seed data anywhere in `server/src` reference it. There is currently **no mechanism at all** linking any login to a retailer, and no seeded "Retailer" role exists anywhere (`server/src/db/seed/index.ts` only ever creates the tenant's system "Owner" role and one "Admin" user holding it; the Phase 2 retailer ETL — `server/src/db/etl/retailers.ts` — only migrates the `retailers` business-entity rows, never creates `users`/`retailer_users` rows). This workstream is not "tighten an existing isolation mechanism" — it is building the retailer identity/data-linkage layer for real, for the first time, *and then* enforcing on top of it.
- **Every retailer-scoped list/get today is unenforced by construction**: `GET /customers`, `/orders`, `/invoices`, `/shipping-boxes` all accept an **optional, client-supplied** `retailerId` query param with zero cross-check against the caller's own identity (confirmed directly in each `*.routes.ts`) — a session can currently request any retailer's data, or omit the param and see everyone's, gated only by whatever generic permission (`orders.view`, `invoices.view`, `shipping.manage`, or nothing at all for customers) it holds.
- **Catalog reads (`GET /products`, `GET /features`, etc.) are gated by `authenticate` only** — confirmed via each route file's own doc comment ("Reads are gated by `authenticate` only... browsing the catalog is expected of any logged-in staff/retailer user").
- **`orders.edit` is already a reserved-but-unbacked permission key** in `server/src/db/seed/permissions.ts` — same "dead reservation" shape Phase 8 Group 5 found for `catalog.retailer_pricing.manage`, except this one gets a real purpose in this phase rather than being removed.
- **No order-edit capability of any kind exists today** — `orders.routes.ts` has exactly 2 GETs, 1 POST (create), 1 POST (pdf). `OrderDetailPage.tsx` is read-only plus PDF-generate plus Repeat.
- **Permission gaps found**: `invoices.view` already exists (retailer-safe, view-only). **`shipping.view` does not exist** — only `shipping.manage` (pack/close boxes), so giving a retailer view-only access to their own shipping records without also granting factory-floor write capability needs a new permission key.

## Key architectural decisions

**1. User→retailer linkage & cardinality** — keep `retailer_users` (its M:N shape already matches `REWRITE_ARCHITECTURE.md` §2's stated intent: "a retailer can have multiple staff logins later"), but add a **unique index on `retailer_users.userId`** — enforcing the user's decision ("pinned to exactly one `retailerId`") on the user side of the relationship only, leaving the retailer side (many users per retailer) unconstrained, matching the table's original design intent. Safe/additive: confirmed zero existing rows anywhere to violate it. Resolve `actor.retailerId` **once**, inside `authenticate` middleware (a follow-up lookup against `retailer_users` for `actorType === "user"`; tailors have no retailer concept, stays `null`), extending `req.actor` from `{ id, tenantId, actorType }` to `{ id, tenantId, actorType, retailerId: string | null }` — available to every route/service for free, the same way `tenantId` already is, rather than each call site re-querying it.

**2. Building the write path for this linkage (doesn't exist at all today)** — `users.service.ts#createUser`/`updateUser` and `users.routes.ts`'s schemas grow an optional `retailerId`; when provided, upsert-replace the user's one `retailer_users` row (matching the new unique constraint); when explicitly cleared, remove it (converting a retailer user back to staff is a legitimate operation — role/permission assignment is already independent, via `user_roles`). `UsersPage.tsx` gains a retailer picker in its create/edit form.

**3. The core enforcement mechanism** — identity-based, **not** a new permission. Concretely: `customers.service.ts`, `orders.service.ts`, `invoices.service.ts`, `shipping.service.ts`'s list/get functions get `actor.retailerId` threaded down (the exact same pattern `actor.tenantId` already flows through every one of them) with this rule: **if `actor.retailerId` is non-null, force every retailer-scoped query's `WHERE retailerId = ...` to `actor.retailerId`, ignoring whatever the client sent in the query string/body**; if `null` (a staff/admin, not retailer-linked), behave exactly as today. This is deliberately not a grantable permission (no `customers.own_only` key) — it's an identity fact about the actor, the same category of thing `tenantId` already is. Single-resource fetches (`getCustomer(id)`, `getOrder(id)`, etc.) apply the retailer condition **inside the query's own `WHERE`** (not a fetch-then-403-check) so a cross-retailer resource is genuinely never returned — the caller gets the same 404 an actually-missing resource gets, mirroring how tenant isolation already works (a cross-tenant row isn't fetched at all, not fetched-then-rejected) rather than introducing a new way to leak a resource's existence via a 403/404 distinction.
   - **Retailer's own profile self-edit**: `retailers.service.ts#updateRetailer` gets an identity-based allowance — `actor.retailerId === id` is sufficient even without `retailers.manage` — same category of rule as above, not a new permission.

**4. Catalog admin lockdown — worked through concretely, per the user's explicit ask** — the crux: `GET /products`, `GET /features?productId=`, etc. are called both by admin pages and by the order-builder, on the literal same route with the literal same request shape; there is no reliable server-side signal distinguishing the two callers. **Decision: don't attempt to.** These reads stay open to any authenticated actor — gating them would break order creation, which legitimately needs this same catalog data. What actually changes:
   - **Frontend**: wrap the catalog admin routes (`/catalog/products`, `/catalog/super-products`, `/catalog/processes`, `/catalog/measurements`, `/catalog/features`, `/catalog/fittings/*`, `/extra-payment-categories`, `/tailors`) in `RequirePermission` (already the established pattern — confirmed already applied to Retailers/Users/Roles/Tailors routes in `AppRoutes.tsx`; needs auditing/completing for the rest of the catalog routes specifically). A retailer user, holding none of these `.manage` permissions, is routed away exactly like every other admin-only page today.
   - **Backend — the part that's the actual security boundary**: nothing new to build here. The "core permission" the user refers to is real, but it already exists and is already correct: retailers must simply never hold any `catalog.*.manage` permission, so they can read-but-never-mutate catalog data through either the admin routes or the order-builder's identical routes — this was already the deliberate Phase 5 design (reads open, writes gated). **This workstream's actual new work here is a verification/seed task** (confirm, via a real test against the newly-seeded Retailer role, that it holds zero `catalog.*.manage` grants), not a new backend read-gating mechanism — because one that could actually distinguish "admin page" from "order-builder" traffic on an identical request isn't buildable, as reasoned above.

**5. Admin cannot create orders, only modify existing ones** — worked through against the real current state (no edit capability exists at all, `orders.edit` is a reserved-not-built permission). Decision: this is genuinely two changes, not one —
   - `orders.create`: a **seed-default** change, not a hardcoded restriction — the tenant-configurable "Admin" role (as seeded/pre-built for a new tenant) stops being granted `orders.create` by default; the system "Owner" role is unaffected (stays maximal, per its Phase 8 Group 3 protection); a tenant could still grant `orders.create` to a custom role later, since this rewrite's whole RBAC model is tenant-configurable bundles, not hardcoded role behavior. `/orders/new`'s existing `RequirePermission permission="orders.create"` needs no code change — it already does the right thing once the seeded grant changes.
   - `orders.edit`: goes from reserved to real. **Decided (2026-08-16), after user review — the full edit wizard, not a narrow action set.** Admin gets a real, full re-edit surface for an existing order's measurements and styling: add/remove line items or units, re-open and edit any unit's shared measurements, re-open and edit any unit's fabric/styling — a genuine second entry point into Phase 9's own order-builder machinery (`LineItemMeasurementsPanel`/`StylingAccordion`/`OrderCartStep`), operating in "edit an existing order" mode (PATCH/PUT-ing the existing order) instead of "create a new order" mode (POST-ing a new one), rather than a second, parallel implementation of the same measurement/styling UI. The narrow status/cancel/reassign action set is **also** built (not replaced by the above) — still needed regardless, e.g. for the "Modified" status transition Workstream B's PDF banner depends on. **Manual Size (legacy's `editOrderWithManualSize.jsx`) folds into this same edit surface**, matching legacy's own real design of combining both concerns on one admin order-edit page — see Group 6 below for the concrete mechanism (confirmed from source: `siamClient/src/components/superAdmin/pages/order/editOrderWithManualSize.jsx`, 3476 lines, read in full).
   - **Manual Size, concretely, from source**: legacy's version is a per-product static line-drawing diagram (hardcoded one image per literal product name — `Jacket`/`Pant`/`Shirt`/`Vest`/etc. — the same by-name-branching pattern this whole rewrite exists to eliminate), which an admin annotates with free-floating draggable text/number labels (`react-draggable`; numbers auto-converted to a reduced mixed fraction like "1½"), then rasterizes client-side into one flattened PNG (`html-to-image`'s `toPng()`) and uploads through a dedicated legacy endpoint (`POST /image/uploadManualImage`), storing the resulting URL directly on the order (`manualSizeObject`, itself keyed by literal item name). **Confirmed this exists only in the admin edit page** — never in `Step4.jsx` (order creation, already reviewed for Phase 9) and never pushed to any customer-level canonical record (unlike measurements, which legacy explicitly pushes to `PUT /userMeasurement/updateCustomerMeasurementsSingle/:customerId`). It is therefore **order-scoped, not a cross-order customer default** — it does not belong in Workstream D's profile table, and does not auto-carry-forward between orders the way Workstream D's measurements do. Generic replacement: a new `products.measurement_diagram_image` (admin-configurable, distinct from the existing general `products.image`) replaces legacy's hardcoded per-name static image imports; one generic annotation-editor component (no per-product-name branching) is reused for whichever component's product is being edited; rasterization reuses `html-to-image` (not currently a client dependency — confirmed via `client/package.json`, needs adding, along with `react-draggable`) the same way legacy did; upload targets the **already-built generic `POST /api/uploads`** (Phase 9 Group 1) — no second, bespoke upload endpoint. Storage: per the user's own framing ("irrespective of quantity, like measurements"), this is **shared per line item**, not per physical unit — follows the exact same denormalize-at-submit pattern Phase 9 already established for `measurementNote` (one shared value, copied identically into every sibling unit's own row), not the per-unit `referenceImage` pattern. New column: `order_item_components.manual_size_image` (nullable text URL).

**6. What retailers can do** — own customers (create/view/edit, via the identity-based rule in Decision 3), own orders (create/view via the order-builder, `orders.create` stays on the Retailer role per Decision 5), own invoices (`invoices.view`), own shipping (new `shipping.view`, see current-state findings), own profile/logo (Decision 3's self-edit rule), group orders (data/permission-level only — the frontend page itself remains a known, separately-tracked gap per Phase 8, not built here).

**The exact refactor, and why:** `CreateComponentInput`/`CreateOrderItemInput` (`orders.service.ts`) each grew one optional field — `id?: string` — and `CreateComponentInput` also grew `manualSizeImage?: string`. These are the same two interfaces `resolveItemsFromInput` (catalog validation) has always taken; `create`'s own route still never populates `id` (its zod schema doesn't accept it), so `buildOrder`'s behavior is provably unchanged (see regression numbers below). `ResolvedItem`/`ResolvedComponent` carry both fields straight through `resolveItemsFromInput` unchanged otherwise — this is the "one real resolver for both create and edit" the task asked for, not a second copy. The actual per-component *write* logic (profile upsert, `changedFromProfile`, measurement/feature rows) was extracted out of `buildOrder`'s loop into a new function, `writeComponentContent(tx, tenantId, customerId, productId, orderItemComponentId, component)`: it unconditionally deletes any existing `order_item_component_measurements`/`order_item_component_features` rows for that component id (a no-op for `buildOrder`'s always-fresh components), then upserts the profile and inserts the submitted rows — identical logic, now called from both `buildOrder` (after an `INSERT`) and the new `editOrderItems` (after either an `INSERT` or an `UPDATE`). This is the one piece of genuinely shared, correctness-sensitive logic (the profile-upsert/`changedFromProfile` computation) the task called out — item/component orchestration itself (insert-only for create vs. insert-or-update-or-delete for edit) is structurally different between the two paths and was **not** forced into one function, since doing so would have obscured both without actually removing duplication (there was none to remove there — `buildOrder`'s insert loop is unchanged, just calling the extracted helper).

`editOrderItems(tenantId, orderId, { items }, actorRetailerId)` is a true **reconciliation**, not a delete-and-recreate: it calls `resolveItemsFromInput` (identical catalog validation to create) against the submitted `items[]`, then diffs the result against the order's real current `order_items`/`order_item_components` (fetched via `requireOrder` + a direct query, isolation-scoped exactly like `getOrder`). An item/component carrying its own real `id` is matched, validated to belong to this order (422 `ORDER_ITEM_NOT_FOUND`/`ORDER_ITEM_COMPONENT_NOT_FOUND` otherwise — never a silent cross-order write), and updated in place — critically, its `manufacturing_steps` rows are **never touched**, preserving any real shop-floor progress. An item/component with no `id` is a genuine addition, written exactly like `buildOrder` does (fresh `INSERT` + fresh `manufacturing_steps`). An existing item/component whose `id` is absent from the submitted set is removed (bottom-up: steps → measurements → features → component/item row, matching this codebase's established no-cascading-deletes teardown order). A kept item's `superProductId` is immutable (422 `ORDER_ITEM_SUPER_PRODUCT_IMMUTABLE` if the client tries to change it — remove and re-add instead, since changing it would silently invalidate its whole component set). On any successful write, the order's own row gets `status: "Modified"` and `lastModifiedAt: new Date()`.

**A design choice made and disclosed, not guessed silently:** the task's own language ("re-submit any unit's shared measurements — still denormalized across sibling units") could be read as asking for automatic server-side propagation of an edited measurement to sibling units the client didn't even mention. Rereading `orders.service.ts`'s actual `create`-path behavior (and its own "shared/per-unit correctness" test) shows this "denormalization" has only ever been a **client-driven** convention — the create path stores exactly what's submitted per component, with no cross-component logic at all; a quantity-N line item ends up byte-identical across siblings only because the (Phase 9) client submits the same values N times in one request. There is also no schema concept of "line item" as a durable id to key an auto-propagation mechanism off of (only `order_items` rows sharing a `superProductId`, which isn't a safe proxy — two different real line items can share a `superProductId`, e.g. re-ordering the same suit twice with different measurements should not couple them). Introducing real server-side "propagate an edit to components the caller didn't mention" would be a new mechanism with no existing precedent and a real correctness downside (an admin editing one unit's measurement without being able to intentionally diverge from its siblings). **Decision made:** the edit route follows the exact same contract as create — the caller resends the full state of every unit it wants to keep, `writeComponentContent`'s delete-then-insert stores exactly what's given per component, and "denormalized across siblings" is proven the same way the create-path test proves it (mirrored below): resending identical values across several sibling units in one request produces byte-identical stored rows. This matches 6.3's stated design (Phase 9's `LineItemMeasurementsPanel`, one shared panel feeding every sibling unit, re-hosted in edit mode) — the frontend, not new backend logic, is what will make "editing a line item's shared measurements" feel like one action. Flagged here in case the architect intended literal auto-propagation instead.

**A second judgment call, disclosed:** `reassignOrderRetailer` does a plain `orders.retailer_id` swap with no re-validation against the order's `customer_id`'s own (fixed, non-reassignable) `retailer_id` — enforcing that match would make the action a no-op, since `buildOrder` already guarantees they're equal at creation and `customers.retailer_id` never changes afterward. This means a reassigned order can end up pointing at a different retailer than its own customer record. The task named this action explicitly ("reassign retailer (`retailerId`)") with no further spec; implemented literally, consequence disclosed rather than silently resolved either way.
